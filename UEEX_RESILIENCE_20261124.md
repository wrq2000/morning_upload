# Изоляция источников и внутренняя ошибка API УЭБ — 24.11.2026

## Причина сбоя

В приложенном логе УЭБ получил для ID `2216577956` ответ API с полем `Message`:
`PrepareAuction … LogCollection.Getdata … Empty member`.
Отдельная проверка текущего публичного обработчика также вернула HTTP 200 и JSON
с этой внутренней ошибкой. Это ответ сервера биржи, не пустая таблица торгов,
не ошибка SSH-аутентификации и не свидетельство отсутствия продаж.

До исправления исключение отменяло сбор остальных аукционов УЭБ. Остальные процессы
приложения в этом конкретном запуске уже завершились успешно, что видно в итогах лога.
Дополнительно усилена общая изоляция: теперь даже необработанное исключение в обёртке
процесса не прерывает другие задачи.

## Что изменено

### Общий запуск

`common/process_runner.py` выполняет все включённые задачи через
`asyncio.gather(..., return_exceptions=True)`. Для каждого исключения создаётся отдельный
результат с ошибкой; приложение ждёт завершения остальных задач и выводит общий итог.
Некорректный результат задачи и отсутствующая функция также не отменяют соседние задачи.
После завершения всех задач общий проход возвращает 0, включая обработанные сбои
отдельных источников. Предупреждения сохраняются в логах и результатах задач.
Подробности актуального поведения — `WARNING_EXIT0_20261124.md`.

В `main.py` изменён только механизм запуска и отображение частичного статуса.
**При замене main.py сохраните ваш собственный список ENABLED_PROCESSES:**
в полном архиве остаётся стандартный список текущего проекта. Ваши локальные
комментарии включения/отключения источников по логу восстановить однозначно нельзя.

### Внутри УЭБ

Каждая дата календаря, объявление и аукцион обрабатываются отдельно. Ошибка сохраняется
в журнале, после чего сбор продолжается. Ответ HTTP 200 с `Message` вызывает отдельный
`AuctionApiError`. Для него выполняются короткие повторы:

```dotenv
UEEX_API_ERROR_ATTEMPTS=2
UEEX_API_ERROR_BACKOFF=5
```

Это значения по умолчанию; добавлять их в `.env` необязательно. Они независимы от
повторов сетевых ошибок/HTTP 429/5xx в `HttpClient`. При повторе создаётся новый
`DataGateway`, чтобы не переиспользовать завершившуюся с ошибкой задачу.
Ошибки валидации/обработки не застревают в checkpoint: такой ответ удаляется из
промежуточного кеша и при следующем запуске запрашивается заново.

### Полная и частичная выгрузки

- Полный сбор публикует прежний `ueex_gas_export.csv`.
- При ошибках публикуется отдельный `ueex_gas_export_partial.csv`.
- Основной CSV последнего полного сбора при частичной выгрузке не меняется.
- В частичный CSV входят успешно проверенные аукционы и сохранённая история вне окна.
- Сбойные аукционы исключаются из частичного CSV. Их последняя исправная исходная
  версия сохраняется в `ueex_gas_export_state.json`; её строки не выдаются за обновлённые.
- Отсутствующий ответ не превращается в нулевой проданный объём и не считается торгами
  без продаж. Настоящий успешный ответ с нулевыми продажами по-прежнему учитывается как торги.

Формат столбцов CSV сохраняется. В `gas_data_duty` частичный файл загружается тем же
обработчиком UEEX; отсутствующие в CSV строки из БД не удаляются. Данные сбойного
аукциона в БД не заменяются устаревшей копией из кеша.

### Письма и состояние

Доступный частичный CSV отправляется обычным получателям. В теме добавляется
`[НЕПОЛНЫЕ ДАННЫЕ]`, в теле указываются ошибки, номера/ID, а также прямо говорится,
что отсутствие новых торгов подтвердить нельзя. Имя вложения содержит дату, например:

`ueex_gas_export_partial_2026-11-24_110223_123456.csv`

Если доступных строк нет, CSV содержит только заголовок, а письмо всё равно сообщает
о неполном сборе. Нулевые результаты вместо пропущенных данных не создаются.

`last_success_msk` и `last_discovery_through` в состоянии сбора обновляются только
при полном успехе. Для каждой попытки отдельно хранятся `last_attempt_msk`,
`last_attempt_through`, `collection_complete`, `collection_errors`, `excluded_auction_ids`.
При частичной ошибке checkpoint остаётся, поэтому повтор того же прохода продолжает
работу с сохранёнными исправными ответами. Окно по-прежнему задаётся `UEEX_RECHECK_DAYS`
и автоматически не расширяется.

В `ueex_mail_state.json` фиксируется доставка частичного письма, но
`last_reported_check` не сдвигается: сравнение торгов остаётся привязано к последнему
полному отправленному отчёту. Частичный отчёт не считается успешной полной проверкой.
Повторное одинаковое частичное письмо в тот же день не дублируется; после восстановления
данных отправляется полноценный отчёт. Для полных отчётов прежний fingerprint сохранён.

## Установка

Замените файлы патча. Существующие `.env`, CSV и JSON-состояния сохраняются;
удалять их не требуется. В `main.py` перенесите ваш текущий `ENABLED_PROCESSES`.

При запуске из PyCharm запустите прежний `main.py`.
Для Docker после установки файлов пересоберите образ:

```bash


cd /home/vologzhaninov_as/projects/morning_upload
docker build --progress=plain -t morning_upload:latest .


```

Ручной запуск (отправляет письма включённых процессов):

```bash


cd /home/vologzhaninov_as/projects/morning_upload
MORNING_IMAGE=morning_upload:latest bash ./run.sh


```

Расписание cron и настройки VPN не меняются.

## Проверка

В 14 контролируемых тестах проверены реальные DataGateway, парсеры, обработка чисел/переводов,
состояния, checkpoint и MIME-письма. HTTP и SMTP в тестах заменены тестовыми источниками:
реальные письма и SSH-подключения к вашим серверам не выполняются.

Проверены: сохранение 47 доступных позиций из 48 при сбое одного аукциона;
продолжение последующих аукционов; сохранность полного CSV и старого снимка; восстановление
всех 48 позиций; отказ календаря/объявления; ошибка обработки; отказ всех результатов API;
успешный аукцион без продаж; повтор внутренней ошибки на новом DataGateway;
доставка частичного письма без ложной отметки полного успеха; независимое завершение
остальных процессов при неожиданном исключении одного источника.
